# EMS 기준정보 관리 체계 설계안 (초안)

- 작성일: 2026-11-13
- 상태: 초안 (논의 정리용)
- 목적: 여러 사이트에 공통으로 적용하는 EMS 기준정보 관리 체계를 정의하고, 온보딩의 시작점으로 삼는다.
- 근거: 에너지 모니터링 시스템의 일반적인 설계 관행과 지금까지의 논의. 특정 제품의 사양을 검증한 문서는 아니다.

---

## 1. 목적과 범위

### 1.1 해결하려는 문제
- 현장에서 올라오는 데이터 이름(raw)은 약어이거나 사이트마다 제각각이라 그대로 쓰기 어렵다.
- 같은 데이터를 전력, 조직, 공간 등 여러 관점에서 동시에 봐야 한다.
- 사이트마다 기준정보를 새로 설계하면 온보딩이 SI 성격으로 흐른다.
- 이후 기능(피크 제어, 베이스라인, KPI, ISO 50001 증적)이 모두 기준정보 위에서 동작한다.

### 1.2 범위
| 포함 | 제외 |
|---|---|
| 수집 원천, 표준 포인트, 설비, 계층(뷰), 코드, 이력, 검증, 온보딩 절차 | 수집 게이트웨이 구현, 시계열 저장 방식, 대시보드 UI |

---

## 2. 설계 원칙

1. **원천과 의미를 분리한다.** 현장 태그(raw)는 바뀔 수 있으므로 우리가 정의한 표준 포인트와 별칭 대응표로 연결한다.
2. **ID와 이름을 분리한다.** 모든 엔티티는 의미 없는 고유 ID를 갖고, 이름과 코드는 속성으로 둔다.
3. **하나의 데이터, 여러 관점.** 포인트를 관점마다 따로 연결하지 않고 설비를 중심에 두어 설비를 각 관점에 배치한다.
4. **경로 코드는 만들어지는 값이다.** 각 노드가 자기 코드를 갖고, 경로는 부모 코드를 이어 자동 생성한다.
5. **코드는 데이터로 관리한다.** 코드 값, 분류, 규칙을 화면에서 관리하고 소스에 하드코딩하지 않는다.
6. **모든 변경에 유효 기간을 둔다.** 소속과 연결이 바뀌어도 과거 집계가 흔들리지 않게 한다.
7. **등록 → 검증 → 승인 → 적용.** 변경은 검증을 통과한 뒤 승인된 시점부터 반영한다.
8. **표준과 확장을 구분한다.** 공통 표준(템플릿, 표준 코드)은 고정하고 사이트 고유 항목은 정해진 범위에서만 확장한다.

## 3. 전체 구조

```
[1] 수집 원천        장치 · 원천 태그(raw) · 별칭
        ↓ 변환(별칭 대응)
[2] 표준 포인트      의미 · 단위 · 계측 성격 · 배율        ← 고유 ID
        ↓ 연결
[3] 설비(자산)       유형 · 용량 · 속성
        ↓ 배치
[4] 뷰(계층)         전력계통 · 공간 · 조직 · 공정 … (뷰 정의로 추가 가능)
        ↓ 부가
[5] 목적 속성        피크 제어 · SEU · KPI · 베이스라인 · 알람

[공통] 코드 관리 · 이력 관리 · 검증 · 감사 로그
```

변경 최소화 효과:
- 부서나 위치가 바뀌면 설비의 배치만 바꾼다. 포인트는 건드리지 않는다.
- 설비를 교체하면 포인트 연결만 이동한다. 계층 배치는 유지된다.
- 현장 태그가 바뀌면 별칭 대응표만 고친다.

## 4. 핵심 엔티티 (테이블 후보)

주요 컬럼만 표시한다. 모든 테이블은 공통으로 `id`, `사이트 ID`, `사용 여부`, `생성/수정 일시·사용자`를 가진다.

### 4.1 사이트
| 컬럼 | 설명 |
|---|---|
| 사이트 코드 / 명 | 고유 코드 |
| 시간대 | 집계 기준 |
| 계약 정보 | 계약전력, 요금제, 단가 (유효 기간 포함) |

### 4.2 수집 원천
| 엔티티 | 주요 컬럼 |
|---|---|
| 수집 장치 | 장치 ID, 유형(게이트웨이/계측기/PLC), 프로토콜, 수집 주기 |
| 원천 태그 | 원천 태그 ID, 장치, **raw 이름**, 원천 주소, 데이터 타입, 원천 단위 |
| 별칭 대응 | 원천 태그 → 표준 포인트, 유효 기간 |

### 4.3 표준 포인트
| 컬럼 | 설명 |
|---|---|
| 포인트 ID | 의미 없는 번호 (예: PT-000123) |
| 표준명 | 우리가 관리하는 파라미터명 |
| 측정 항목 코드 | 전력, 전력량, 유량, 압력, 온도 등 |
| 계측 성격 | 순시 / 누적 / 구간 |
| 단위, 배율, 오프셋 | 변환 규칙 |
| 롤오버/교체 처리 | 누적값 단절 대응 |
| 데이터 품질 규칙 | 범위, 결측 허용 |

### 4.4 설비(자산)
| 컬럼 | 설명 |
|---|---|
| 설비 ID, 설비 코드 | 고유 식별 |
| 설비 유형 코드 | 변압기, VCB, 컴프레서, 압연기 등 |
| 속성 | 정격 용량, 제조사 등 (유형별 확장) |
| 포인트 연결 | 설비 ↔ 표준 포인트, 역할(주계량/보조), 유효 기간 |

### 4.5 뷰(계층)
| 엔티티 | 주요 컬럼 |
|---|---|
| 뷰 정의 | 뷰 코드, 뷰명, 분류(물리/위치/책임) |
| 노드 | 노드 ID, 뷰, 부모, **노드 코드**, 노드명, 노드 유형 코드, 순서 |
| 경로 | 노드의 전체 경로 코드(자동 생성값, 조회 성능용 저장) |

노드는 부모를 하나만 갖는다.

### 4.6 설비 배치
| 컬럼 | 설명 |
|---|---|
| 설비 ID, 노드 ID | 어느 뷰의 어느 노드에 속하는가 |
| 합산 부호 | + / − (차감 구조 대응) |
| 배분율 | 공유 설비를 여러 노드에 나눌 때의 비율 (합 100%) |
| 유효 시작/종료 | 이력 관리 |

### 4.7 그룹·태그
계층이 아닌 횡단 분류 (피크 제어 대상, 주요 에너지 사용처(SEU), KPI 대상 등). 설비나 포인트에 붙인다.

### 4.8 계산 포인트(가상 포인트)
| 컬럼 | 설명 |
|---|---|
| 수식 | 합산, 차감, 비율, 원단위 |
| 입력 포인트 | 참조 대상 |
| 버전, 유효 기간 | 수식 변경 이력 |

### 4.9 목적 속성
| 용도 | 속성 예 |
|---|---|
| 피크 제어 | OFF 가능 여부, 우선순위, 감축 kW, 복귀 조건 |
| 베이스라인/KPI | 대상 지표, 보정 변수 연결, 목표 |
| 알람 | 임계값, 지속 시간 |
| ISO 50001 | 주요 에너지 사용처 여부, EnPI 연결 |

### 4.10 코드
| 엔티티 | 주요 컬럼 |
|---|---|
| 코드 그룹 | 그룹 코드, 이름, 표준/로컬 구분, 값 형식 규칙 |
| 코드 값 | 값 코드, 표시명, 상위 코드, 정렬, 사용 여부, 유효 기간 |

### 4.11 변경 이력·감사
| 컬럼 | 설명 |
|---|---|
| 변경 요청 | 요청자, 대상, 변경 전/후, 적용 예정일 |
| 승인 | 승인자, 일시, 반려 사유 |
| 감사 로그 | 모든 마스터 변경 기록 |

## 5. 코드 체계

### 5.1 코드의 종류
| 종류 | 용도 | 예 |
|---|---|---|
| 공통 코드 | 선택 목록 값 | 에너지원, 단위, 설비 유형, 계측 성격, 노드 유형, 연결 역할 |
| 노드 코드 | 계층 안에서의 위치 식별 | TR1, LV1, MCC1 / 압연공장, 압연공정, 압연기1 |
| 경로 코드 | 노드 코드를 이어 만든 값 | TR1_LV1_MCC1 |

### 5.2 규칙
- 노드 코드는 **같은 부모 아래에서 유일**해야 한다.
- 허용 문자, 길이, 구분자는 코드 그룹별 규칙으로 정의하고 입력 시 검증한다.
- 코드는 **삭제하지 않는다.** 사용 중지 처리하고 유효 기간을 종료한다.
- 변경 전에 **영향 범위**(해당 코드를 쓰는 포인트·설비·노드 수)를 보여 준다.
- 공통 코드는 표준(본사 정의)과 로컬(사이트 추가)로 구분한다. 로컬은 접두어로 충돌을 막는다.

### 5.3 예시
| 항목 | 값 |
|---|---|
| raw 이름 | RM1_KW_01 |
| 표준 포인트 | PT-000123 / 압연기1 순시 전력 / kW / 순시 |
| 설비 | 압연기1 (설비 유형: 압연기) |
| 전력 뷰 경로 | TR1_LV1_MCC1 |
| 조직 뷰 경로 | 압연공장_압연공정_압연기1 |
| 그룹 | 피크 제어 대상, SEU |

## 6. 이력 관리

- 설비 배치, 포인트 연결, 별칭 대응, 계산 수식, 사이트 계약 정보는 모두 **유효 시작/종료일**을 가진다.
- 집계는 **조회 시점이 아니라 데이터 시점의 구조**로 계산한다. 예: 3월에 설비가 A팀에서 B팀으로 이동하면, 2월 데이터는 A팀 소속으로, 4월 데이터는 B팀 소속으로 집계된다.
- 변경은 미래 시점으로 예약할 수 있고, 승인 후 해당 시점에 자동 반영된다.
- 과거 구조 변경은 별도 권한과 사유 기록을 요구한다.

## 7. 온보딩 프로세스

| 단계 | 내용 | 산출물 | 검증 |
|---|---|---|---|
| 1. 사전 진단 | 사이트 구조, 계측 현황, 수집 방식 파악 | 사이트 진단서, 계측점 목록 | 계측점 누락 여부 |
| 2. 수집 원천 등록 | 장치·원천 태그 일괄 등록 (엑셀/자동 수집) | 원천 태그 목록 | 중복 주소, 데이터 타입 |
| 3. 표준 포인트 변환 | raw → 표준명 제안(약어 사전·패턴) → 담당자 승인 | 별칭 대응표 | 단위 누락, 계측 성격 |
| 4. 설비 정의 | 설비 목록, 유형 템플릿 적용, 포인트 연결 | 설비 마스터 | 필수 포인트 세트 충족 |
| 5. 뷰 구성 | 전력, 공간, 조직 등 계층 생성, 설비 배치 | 계층 구조, 경로 코드 | 부모 유일성, 순환, 배분율 합 |
| 6. 목적 속성 설정 | 피크 대상, SEU, KPI 대상, 알람 | 속성 설정서 | 대상별 필수 항목 |
| 7. 통합 검증 | 합산 정합성, 결측, 단위 일관성 점검 | 검증 리포트 | 아래 8장 규칙 |
| 8. 승인·적용 | 변경 요청 → 승인 → 적용 시점 확정 | 적용 이력 | 승인자 확인 |
| 9. 운영 전환 | 대시보드·집계·기능 모듈 연결 확인 | 인수 확인서 | 현장 확인 |

- 2~6단계는 **엑셀 일괄 등록 + 템플릿**을 기본으로 하고, 화면 편집은 보정에 쓴다.
- 기간과 인력은 사이트 규모에 따라 달라지므로 진단 단계에서 산정한다. (별도 확정 필요)

## 8. 검증 규칙

| 구분 | 규칙 |
|---|---|
| 연결 | 미연결 포인트, 설비 없는 포인트, 포인트 없는 필수 설비 |
| 코드 | 코드 규칙 위반, 같은 부모 아래 코드 중복, 사용 중지 코드 사용 |
| 구조 | 순환 참조, 부모 없는 노드, 배분율 합이 100%가 아님 |
| 단위·성격 | 단위 누락, 계측 성격과 단위 불일치(누적값에 kW 등) |
| 이력 | 유효 기간 겹침, 공백 기간 |
| 정합성 | 상위 노드 값과 하위 합계의 차이 (허용 오차 초과) |
| 별칭 | 하나의 원천 태그가 둘 이상의 표준 포인트에 연결 |

심각도(오류/경고)를 구분해 오류가 있으면 승인 요청을 막는다.

## 9. 화면 구성 (프론트)

| 메뉴 | 주요 기능 |
|---|---|
| 사이트 설정 | 사이트 속성, 계약 정보 |
| 코드 관리 | 공통 코드, 노드 코드 규칙, 영향 범위 조회, 이력 |
| 수집 원천 | 장치·태그 목록, 엑셀 일괄 등록 |
| 표준 포인트 | raw → 표준명 제안, 승인, 단위·성격 설정, 템플릿 적용 |
| 설비 관리 | 설비 목록, 유형 템플릿, 포인트 연결 |
| 계통 편집 | 뷰 선택, 트리 편집, 설비 배치, 경로 코드 표시 |
| 그룹·목적 속성 | 피크 대상, SEU, KPI 대상 |
| 검증 | 규칙별 결과, 오류 위치 이동 |
| 변경 이력·승인 | 요청 목록, 비교, 승인/반려, 적용 예약 |

화면 목업: 계통 편집 · 포인트 매핑 화면은 별도 작성되어 있다. 설비 중심 매핑, 수집 원천 변환, 코드 관리 화면은 추가 예정이다.

## 10. 백엔드 구성

- **마스터 API:** 엔티티별 조회/등록/수정, 일괄 가져오기·내보내기
- **검증 엔진:** 8장 규칙을 실행하고 결과를 저장한다. 규칙은 설정으로 추가할 수 있다.
- **변경 관리:** 요청 → 승인 → 적용 예약. 적용 시점에 마스터를 갱신하고 이벤트를 발행한다.
- **마스터 참조 방식:** 수집 파이프라인은 별칭 대응표로 원천 태그를 표준 포인트에 매핑한다. 집계는 유효 기간을 기준으로 구조를 조회한다.
- **캐시와 전파:** 마스터 변경 이벤트로 수집·집계 쪽 캐시를 갱신한다.
- **경로 저장:** 계층 조회 성능을 위해 경로(또는 클로저 테이블)를 함께 저장한다.
- **권한·감사:** 사이트별 권한, 모든 변경의 감사 로그, 과거 구조 수정은 별도 권한.

---

## 11. 표준화 전략

- **설비 유형 템플릿:** 유형별 필수/선택 포인트 세트, 기본 표준명 규칙, 기본 목적 속성을 정의해 사이트에서는 적용과 일부 수정만 한다.
- **약어 사전:** 제조사·사이트별 약어를 축적해 표준명 제안의 정확도를 높인다.
- **표준/로컬 코드:** 공통 코드는 본사 관리, 사이트 고유 코드는 접두어로 분리한다.
- **참고 체계(일반 지식):** Project Haystack, Brick Schema(건물 메타데이터), ISA-95(공장 설비 계층)의 분류 아이디어를 참고하되 그대로 채택하지는 않는다.

## 13. 단계별 구축 방안

| 단계 | 범위 |
|---|---|
| 1단계 (MVP) | 사이트, 수집 원천, 별칭 대응, 표준 포인트, 설비, 전력/조직 뷰, 공통 코드, 기본 검증, 엑셀 일괄 등록 |
| 2단계 | 이력(유효 기간), 변경 승인 흐름, 설비 유형 템플릿, 공간 뷰·뷰 정의 확장, 그룹 태그 |
| 3단계 | 계산 포인트, 목적 속성(피크·KPI·SEU) 연동, 약어 사전 기반 자동 제안 |
| 4단계 | 사이트 간 표준 코드 배포, 영향 범위 분석 고도화, 외부 연계 |

## 14. 주의할 점

- 포인트 이름이나 경로에 의미를 넣어 키로 쓰면 이름 변경 시 연쇄 수정이 생긴다.
- 계층을 설비에 하드코딩하면 관점 추가가 어렵다.
- 이력 없는 구조 수정은 과거 집계와 보고서를 바꾼다.
- 누적 계량의 계기 교체·롤오버 처리를 빼먹으면 집계가 튄다.
- 단위, 배율, 시간대가 사이트마다 달라지면 사이트 간 비교가 불가능하다.
- 화면에 맞춰 테이블이 늘어나면 모델이 흐트러진다. 도메인 모델을 먼저 정하고 화면은 그 위의 뷰로 만든다.
